# Docker Hub: состояние подготовки

**Кандидат для приёмки.** В Dockerfile разделены `package-check` — проверка установки Python-пакета — и `runtime` — доверенный Telegram/HTTP relay с отдельным native-компонентом на компьютере. `package-check` нельзя публиковать как рабочий Desktop-бот. Процедура установки и границы — в [DOCKER](DOCKER.md). Доступность конкретного runtime image и digest подтверждает только соответствующий GitHub Release и результат CI; сам этот файл не подтверждает публикацию.

## Почему нужен компонент на компьютере

Подписанное приложение Codex Desktop и его движок выполняются в пользовательской сессии macOS или Windows. Mac-адаптер проверяет подпись приложения, UID клиента и локальный Unix-сокет. Windows-адаптер использует процесс Desktop, Windows IPC и DPAPI. [Docker Desktop выполняет Linux-контейнер в виртуальной машине](https://docs.docker.com/desktop/features/networking/); настройка томов или сети сама по себе не переносит эти проверки и API. Подмена их отдельным CLI создала бы другие чаты и нарушила основной сценарий продукта.

Схема кандидата: контейнер выполняет Telegram Bot API transport и передаёт HTTP-запросы Mini App; существующая логика бота, локальный контроллер и native adapter остаются на компьютере. Компонент подключается к контейнеру через отдельный ограниченный канал с проверкой подлинности. Профиль Desktop, его ключи и токен внутреннего шлюза контейнеру не передаются. Контроллер на компьютере сохраняет проверку рабочей папки, исходных ID и журнал операций; неизвестный результат не повторяется автоматически.

Контейнер получает BotFather token и является **доверенной частью бота**. Он способен сформировать Telegram initData от имени владельца; повторная проверка HMAC на host не защищает от вредоносного контейнера. Ограничения native scope/permissions сохраняются. Секреты хранятся вне build context, монтируются файлами; runtime работает nonroot/read-only, без Docker socket и без профиля/рабочих файлов.

До объявления Docker основным проверенным способом запуска нужны: успешный runtime smoke в CI, проверенный опубликованный digest Docker Hub, реальный запуск Docker Desktop + native host на каждой заявленной ОС и мобильная приёмка. Mac Apple Silicon/Intel и Windows проверяются отдельно. Реальная связка с личным аккаунтом и физическим Samsung пока не проверена; package-check и синтетические тесты её не заменяют.

Публикация в личный namespace Docker Hub требует точного имени аккаунта и настроенного доступа CI с правом push. [Официальный порядок сборки и push через GitHub Actions](https://docs.docker.com/guides/gha/) использует учётные данные, сохранённые в настройках CI. Значения токенов не публикуются в репозитории и не вставляются в issue или чат.
